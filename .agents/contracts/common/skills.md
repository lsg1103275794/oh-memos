# 通用技能契约

适用于所有任务（代码、文档、调研）。本项目没有前端；后端的专项技能见 [../backend/skills.md](../backend/skills.md)。

## 意图不清楚时：先追问，再动手

**用 `grilling` 技能**（用户说 grill-me 时调用的就是它）。下面任一情况出现时主动调用，不用等用户点名：

- 用户自己还没想清楚要什么：只给了方向（「做好看点」「优化一下」），没有可判断完成与否的标准。
- 需求有两种以上合理理解，而且选错了要返工。
- 工作中发现用户的说法和代码事实、或用户前后的要求互相矛盾。
- 改动会动到数据格式、对外接口、已发布版本、用户数据或磁盘上的大文件，而用户没交代这些边界。

调用时遵守技能本身的规则：一轮问完所有当前能问的问题，每题附推荐答案；**能自己查到的事实自己查，不要问用户**；用户确认达成共识之前不动手。

不需要追问的情况：意图清楚、只是细节没说的，按项目惯例做，并在汇报里说明选了什么。

其他沟通类技能：

| 情况 | 技能 |
|---|---|
| 要追问，同时把结论写成决策记录或术语表 | `grill-with-docs` |
| 用户表示没看懂上一条回复 | `wait-what` |

## 任何代码改动

| 情况 | 技能 |
|---|---|
| 写新功能、修 bug | `tdd-workflow`（先写测试并确认它失败，再实现） |
| 遇到 bug、测试失败、行为异常 | `systematic-debugging`；难查的性能或偶发问题用 `diagnosing-bugs` |
| 声称「完成了」「修好了」「通过了」之前 | `verification-before-completion`（必须有本轮实际运行的命令和输出） |
| 合并前审查自己的改动 | `code-review` |
| 读写项目记忆 | `project-memory`，规则见 [memory.md](memory.md) |

## 选技能的原则

- 技能是手段，不是目的：能用一句命令解决的事不必套技能。
- 一个任务里用了哪些技能、为什么，在最终汇报里提一句，方便用户复查。
- 技能默认的文件位置、提交方式与本目录契约冲突时，以契约为准。
